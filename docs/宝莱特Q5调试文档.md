# 宝莱特 Q5 调试文档

本文用于排查 `aims_jd` 连接宝莱特 BLT Q5 后出现 `java.net.SocketException: Connection reset` 的问题。


参考日志：

## 1. 已确认的 Q5 正常交互

可运行调试程序的行为是：

1. `aims_jd` / 调试程序作为 TCP client 主动连接 Q5：`192.168.0.190:51000`。
2. 使用 HL7 v2.3.1 + MLLP。
3. MLLP 帧格式是：

```text
0x0B + HL7正文 + 0x1C + 0x0D
```

4. 持续发送 HR01 心跳：

```text
MSH|^~\&|||||||ORU^R01|HR01|P|2.3.1|\r
```

5. 连接后发送一次 QY01 查询：

```text
MSH|^~\&|||||||ORU^R02|QY01|P|2.3.1|\r
QRD||R|I|QCM2010|||||RES|\r
QRF|CMS||||0&0^1^1^0^1|\r
```

6. 查询 MLLP 帧尾 `0x1C 0x0D` 后追加 `yyyyMMddHHmmss` 明文时间戳。
7. 调试程序不向 Q5 回 ACK。

## 2. aims_jd 原先的高风险差异

本次排查前，`aims_jd` 和可运行调试程序有几个关键差异：

1. `aims_jd` 每秒都会重复发送 QY01 查询；调试程序只在连接后发送一次。
2. `aims_jd` 会对 Q5 收到的 HL7 消息回 ACK；调试程序不回 ACK。
3. `aims_jd` 原来使用 UTC 生成查询时间戳；调试程序使用本地时间。
4. `aims_jd` 原日志只打印连接成功、HL7 解析结果和 reset，不足以确认 reset 前最后一包到底是什么。

这几个差异都可能导致 Q5 主动 reset 连接。

## 3. 本轮代码默认行为

当前 `application.properties` 中 Q5 相关默认配置已经改成更接近调试程序：

```properties
bltq5.heartbeat.enabled=true
bltq5.heartbeat.interval_ms=1000
bltq5.query.enabled=true
bltq5.query.interval_ms=1000
bltq5.query.timestamp_suffix=true
```

含义：

1. 连接后立即发送一次 HR01 心跳。
2. 延迟 `200ms` 后发送一次 QY01 查询。
3. 后续只继续发送 HR01 心跳。
4. 默认不回 ACK。
5. 打印 Q5 TCP 收发十六进制、HL7 帧摘要、ACK 是否发送。

## 6. connection reset 的常见原因

### 6.1 设备只允许一个客户端

Q5 可能只允许一个 TCP client。如果 `bltq5_debug`、旧系统、`aims_jd` 同时连接同一个 Q5，设备可能 reset 其中一个连接。

排查：

1. 先停止 `bltq5_debug` 和旧系统。
2. 确认只有 `aims_jd` 连接 `192.168.0.190:51000`。
3. 再观察 reset 是否还出现。

### 6.2 Q5 不接受 ACK

调试程序不回 ACK，但 `aims_jd` 原来会回 ACK。部分设备对非预期 ACK 会主动断开。

当前默认：

```properties
bltq5.ack.enabled=false
```

如果日志里出现：

```text
HL7 ACK queued
```

说明 ACK 被打开了。先改回 `false`。

### 6.3 QY01 查询重复发送过快

调试程序只发一次 QY01；`aims_jd` 原来每秒发一次。Q5 可能把重复查询当作异常流量。

当前默认：

```properties
bltq5.query.once_per_connection=true
```

如果要复现旧行为才改成：

```properties
bltq5.query.once_per_connection=false
```

### 6.4 查询时间戳不符合设备预期

调试程序使用本地时间；`aims_jd` 已改为：

```properties
bltq5.query.timestamp.zone_id=Asia/Shanghai
```

如果 reset 紧跟在 QY01 后，可以尝试关闭帧尾明文时间戳：

```properties
bltq5.query.timestamp_suffix=false
```

### 6.5 查询本身触发断开

如果 reset 总是发生在：

```text
BLT Q5 TCP >>> QY01/QCM2010 query
```

之后，先禁用查询，只保留 HR01：

```properties
bltq5.query.enabled=false
```

如果只发 HR01 能稳定连接，问题集中在 QY01 查询帧、时间戳后缀或查询时机。

### 6.6 源 IP 或网络链路差异

Q5 可能只信任旧系统 IP，或者网络中有防火墙/NAT 设备中断连接。

排查：

1. 对比调试程序正常运行时的本机 IP 和 `aims_jd` 运行机器 IP。
2. 看日志里的 `local=/x.x.x.x:port` 是否是 Q5 允许的网段。
3. 同时抓包确认 reset 是 Q5 发出的，还是中间设备发出的。

### 6.7 HL7 字段映射不是 reset 的直接原因

日志里的：

```text
No mapped OBX in HL7 message
```

表示收到的 HL7 没有映射到 AIMS 参数，不等于 TCP reset。比如 `HR01`、`AP01`、`AT01`、`WV01` 本身可能没有 OBX 或没有监护值。

当前 Q5 映射只包含：

```text
NIBPs -> nibp_s
NIBPd -> nibp_d
HR    -> hr
SpO2  -> Spo2
```

调试日志里还出现了 `Resp`、`PR`、`T1`、`T2`、`P1s/P1m/P1d`、`P2s/P2m/P2d` 等，后续如果 TCP 稳定了，可以继续补映射。

## 7. 建议逐项尝试顺序

### 第 1 轮：使用当前默认配置

目标：验证“无 ACK + QY01 只发一次 + 本地时间戳”是否能避免 reset。

需要贴回的日志：

```text
BLT Q5 TCP connect attempt
BLT Q5 TCP >>>
BLT Q5 TCP <<<
HL7 MLLP frame decoded
HL7 ACK not sent
Outbound device session error
```

### 第 2 轮：只保留 HR01 心跳

如果第 1 轮仍 reset，改：

```properties
bltq5.query.enabled=false
```

判断：

1. 稳定：问题集中在 QY01。
2. 仍 reset：问题更可能是连接占用、ACK 之外的设备策略、网络或 HR01 节奏。

### 第 3 轮：打开 QY01，但关闭时间戳后缀

```properties
bltq5.query.enabled=true
bltq5.query.timestamp_suffix=false
```

判断 Q5 是否不接受 `0x1C 0x0D` 后面的明文时间戳。

### 第 4 轮：延迟发送 QY01

```properties
bltq5.query.delay_ms=1000
```

判断是否需要先让 Q5 回几帧后再查询。

### 第 5 轮：必要时复现旧 aims_jd 行为

仅用于对照，不建议长期使用：

```properties
bltq5.query.once_per_connection=false
bltq5.ack.enabled=true
```

如果打开 ACK 或重复查询后 reset 明显复现，就基本可以确认根因。

## 8. 抓包建议

Windows 可用 Wireshark，过滤条件：

```text
ip.addr == 192.168.0.190 && tcp.port == 51000
```

重点看：

1. reset 包的方向：是 Q5 -> aims_jd，还是本机/中间设备发出。
2. reset 前最后一个应用层包：是 HR01、QY01、ACK，还是 Q5 返回的数据。
3. 一次 TCP 包里是否包含多条 MLLP 帧。
4. QY01 后的时间戳是否紧跟在 `1C 0D` 之后。

## 9. 下一步贴日志时保留的信息

请保留完整时间线，不要只截最后一行 reset。至少包含：

1. `Loaded ... active AIMS device definitions`
2. `Connected outbound AIMS device`
3. `BLT Q5 TCP >>>`
4. `BLT Q5 TCP <<<`
5. `HL7 MLLP frame decoded`
6. `HL7 ACK not sent` 或 `HL7 ACK queued`
7. `Connection reset`

根据这些日志可以判断下一步是继续调 QY01、ACK、时间戳，还是转向网络和设备连接占用排查。
