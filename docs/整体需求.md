# AIMS JD 整体需求

## 1. 背景

`aims_jd` 是 AIMS 侧设备采集服务，参考 `C:\Users\gzyrm\Desktop\晶医\icis_repos\icis_jd2` 的工程结构、连接管理、驱动插件、分帧、参数映射和发布分层实现。

与 `icis_jd2` 的关键差异：

- `icis_jd2` 周期性从 `icis_data_bridge` 获取设备定义，并通过 DataBridge gRPC 写入设备数据。
- `aims_jd` 不依赖 `icis_data_bridge`。设备定义来源改为 AIMS 数据库中的 `device_infos` 表，采集结果写入 `device_data` 表。
- `aims_jd` 直接读写 AIMS 引擎 schema。设备定义只读 `device_infos`，不再复制本地快照；采集结果直接写入 `device_data`。

本需求仅描述目标和实现要求，不在本次执行中做代码实现。

## 2. 建设目标

建立 `C:\Users\gzyrm\Desktop\晶医\aims_repos\aims_jd` 项目，作为 AIMS 的独立设备采集进程。

初版目标：

- 从 AIMS 引擎数据库的 `device_infos` 获取启用中的设备信息。
- 周期性从 AIMS 引擎 `device_infos` 刷新内存中的可采集设备集合。
- 根据 `device_driver_code` 加载对应驱动。
- 支持入站 TCP/MLLP 设备和出站 TCP 客户端设备。
- 解析三类首批设备数据。
- 只提取指定监护仪和麻醉机参数。
- 使用 txt 资源文件维护“设备原始编码 -> AIMS 参数编码”的映射。
- 将采集结果写入 AIMS 引擎 `device_data`，其中 `param_code` 使用本需求定义的 AIMS 参数编码。

## 4. 数据库需求

### 4.1 schema 使用方式

`aims_jd` 明确直接读写 AIMS 引擎 schema，不再建立独立业务 schema，也不复制 `device_infos` 快照表。默认配置：

```properties
aims.engine.schema=public
aims.jd.schema=public
```

含义：

- `aims.engine.schema`: AIMS 引擎设备定义表所在 schema，`aims_jd` 只读 `${aims.engine.schema}.device_infos`。
- `aims.jd.schema`: 设备采集数据写入 schema，`aims_jd` 写入 `${aims.jd.schema}.device_data`。
- 当前部署决策为二者均使用 `public`，即只读 `public.device_infos`，写入 `public.device_data`。

`aims_jd` 不负责创建业务表。可选索引 SQL 放置路径：

```text
aims_jd\src\main\resources\config\db\schema.postgresql.sql
```

### 4.2 设备定义来源表

AIMS 引擎侧设备定义表来自：

```text
jingyi_aims_engine\src\main\resources\config\db\schema.postgresql.sql:289-328
```

目标表结构：

```sql
CREATE TABLE device_infos (
    id SERIAL PRIMARY KEY,
    dept_id INTEGER NOT NULL,
    device_sn VARCHAR(255) NOT NULL,
    device_type VARCHAR(255) NOT NULL,
    device_name VARCHAR(255) NOT NULL,
    device_ip VARCHAR(255),
    device_port VARCHAR(255),
    device_driver_code VARCHAR(255),
    source_mode INTEGER NOT NULL,
    source_topology INTEGER NOT NULL,
    upstream_device_id INTEGER NOT NULL DEFAULT 0,
    pds_ip_seq INTEGER DEFAULT 0,
    is_deleted BOOLEAN NOT NULL,
    deleted_by INTEGER,
    deleted_at TIMESTAMP,
    modified_by INTEGER,
    modified_at TIMESTAMP
);
```

`aims_jd` 不复制该表结构，不写该表。设备定义读取规则：

- 周期性从 `${aims.engine.schema}.device_infos` 读取 `is_deleted = false` 的设备。
- 只接收 `device_driver_code` 在 `aims_jd` 支持驱动列表内的设备。
- 不对 `${aims.engine.schema}.device_infos` 做新增、更新、删除。
- AIMS 引擎侧删除或变更为不支持驱动后，下一轮刷新应移除运行态连接或停止对应出站采集。
- 运行态设备以内存中的最近一次查询结果为准。

### 4.3 采集数据写入表

AIMS 引擎侧 `device_data` 表来自：

```text
jingyi_aims_engine\src\main\resources\config\db\schema.postgresql.sql:330
```

目标表结构：

```sql
CREATE TABLE device_data (
    id BIGSERIAL PRIMARY KEY,
    dept_id INTEGER NOT NULL,
    device_id INTEGER,
    param_code VARCHAR(255),
    recorded_at TIMESTAMP,
    recorded_str VARCHAR(255)
);
```

`aims_jd` 不复制该表结构，采集结果直接写入 `${aims.jd.schema}.device_data`。当前配置下即 `public.device_data`。

写入规则：

- `dept_id` 来自设备定义 `device_infos.dept_id`。
- `device_id` 来自设备定义 `device_infos.id`。
- `param_code` 使用本需求第 7 节定义的 AIMS 参数编码。
- `recorded_at` 使用服务器 UTC 时间，由 `aims_jd` 在写入时统一生成。
- `recorded_str` 保存解析后的参数值字符串。
- 不在映射 txt 中的原始参数不写入 `device_data`。
- 空值、无效状态值、解析失败值不写入 `device_data`，但需要输出 debug 日志。
- 同一设备、同一参数、同一分钟内只写入首次解析结果；同一分钟内后续更新跳过；分钟数变化后允许再次写入。
- `device_data` 保留最近 90 天数据，清理任务由外部定时任务或数据库运维手工 SQL 执行，`aims_jd` 初版不内置清理调度。

可选索引用于查询和分钟去重判断，执行前需确认 `public.device_infos` 和 `public.device_data` 已由 AIMS 引擎建表脚本创建：

```sql
CREATE INDEX IF NOT EXISTS idx_aims_jd_device_infos_ip_active
    ON public.device_infos(device_ip)
    WHERE is_deleted = false;
CREATE INDEX IF NOT EXISTS idx_aims_jd_device_infos_driver_active
    ON public.device_infos(device_driver_code)
    WHERE is_deleted = false;
CREATE INDEX IF NOT EXISTS idx_aims_jd_device_data_device_id
    ON public.device_data(device_id);
CREATE INDEX IF NOT EXISTS idx_aims_jd_device_data_recorded_at
    ON public.device_data(recorded_at);
CREATE INDEX IF NOT EXISTS idx_aims_jd_device_data_minute_dedupe
    ON public.device_data(device_id, param_code, date_trunc('minute', recorded_at));
```

## 5. 设备同步与运行态

### 5.1 同步周期

`aims_jd` 应提供设备定义同步配置：

```properties
device.sync.interval_mins=1
device.sync.await_termination_seconds=30
```

刷新线程职责：

- 定时查询 `${aims.engine.schema}.device_infos`。
- 更新内存中的可采集设备集合。
- 对新增设备启动采集。
- 对删除设备、驱动变更设备、IP/端口/source_mode 变化设备关闭旧连接并按新定义重新调度。

### 5.2 设备过滤

初版只采集以下 driver code：

| 设备 | driverCode |
| --- | --- |
| 迈瑞 N12 监护仪 | `JY_monitor_mindray_n` |
| 宝莱特 Q5 监护仪 | `JY_monitor_blt_q5` |
| 迈瑞 WATO EX35/EX55 麻醉机 | `JY_anesthesia_mindray_wato_ex55` |

设备必须满足：

- `is_deleted = false`
- `device_ip` 非空
- `device_driver_code` 非空
- `source_mode in (1, 2)` 初版可直接采集
- `source_mode = 2` 时 `device_port` 必填且为合法端口

`source_mode = 3` 表示不直接通信设备，当前三类样例设备未使用该模式，初版完全忽略，不启动采集连接，也不按 `upstream_device_id` 做中央站扇出关联。

### 5.3 设备来源模式

来源模式含义与 AIMS `device_infos` 保持一致：

| source_mode | 含义 | 初版行为 |
| --- | --- | --- |
| 1 | 采集程序作为服务端 | `aims_jd` 监听 TCP，设备主动连接 |
| 2 | 采集程序作为客户端 | `aims_jd` 主动连接 `device_ip:device_port` |
| 3 | 采集程序不直接通信 | 初版不直接采集，预留上游设备场景 |

来源拓扑含义：

| source_topology | 含义 | 初版行为 |
| --- | --- | --- |
| 1 | 单设备直连 | 支持 |
| 2 | 中央站扇出分发 | 初版仅保留结构，不作为三类设备的主流程 |

入站 TCP 初版使用全局 `tcp.server.port`，不按每台 `source_mode = 1` 设备的 `device_port` 单独监听。入站连接按设备 IP 匹配设备定义，因此直接采集设备的 `device_ip` 必须唯一。

### 5.4 设备样例

示例设备定义：

## 8. 数据写入需求

驱动解析完成后输出统一模型，建议结构：

```text
ObservationBatch
  deptId
  deviceId
  deviceType
  deviceName
  driverCode
  values[]

ObservationValue
  paramCode
  recordedStr
  recordedAt
```

数据库 publisher 负责将 `ObservationBatch` 批量写入：

```sql
INSERT INTO public.device_data (
    dept_id,
    device_id,
    param_code,
    recorded_at,
    recorded_str
) VALUES (?, ?, ?, ?, ?);
```

写入要求：

- 同一批数据使用事务或批量 insert。
- 单个值写入失败时需要记录完整上下文：`device_id`、`driver_code`、`param_code`、`recorded_str`。
- 解析出的未映射参数不写入，但调试模式下应可输出原始编码和值。
- 同一设备、同一参数、同一分钟内后续值跳过，不覆盖已写入值。
- 落库成功后记录批量数量、首个参数、设备 id 和 driver code。

## 11. 日志与可观测性

需要记录：

- 设备定义同步开始、结束、总数、可采集设备数、被过滤设备数。
- 新设备上线、设备定义变更、设备删除、连接关闭原因。
- 入站未知 IP 被拒绝。
- 出站设备连接失败和重连。
- 驱动不支持、参数映射缺失、解析失败、无有效参数。
- `device_data` 批量写入数量和失败上下文。

建议保留 `icis_jd2` 的 Prometheus 指标思路，至少覆盖：

- 当前采集设备数量。
- 在线连接数量。
- 设备同步失败次数。
- 解析失败次数。
- 写库失败次数。
- 未映射参数次数。

## 12. 验收标准

### 12.1 文档和 schema

- `aims_jd` 不创建独立业务 schema，不复制 `device_infos` 或 `device_data`。
- DDL 文件只包含直接读写模式下的可选索引。
- `device_infos` 和 `device_data` 由 AIMS 引擎建表脚本创建。

### 12.2 设备同步

- 能从 AIMS 引擎 `device_infos` 读取示例三台设备并刷新运行态集合。
- 能过滤不支持 driver code 的设备。
- 设备删除或改为 `is_deleted = true` 后，运行态连接被关闭。
- `source_mode = 2` 且端口缺失时不启动采集并记录错误。

### 12.3 驱动采集

- `JY_monitor_mindray_n` 可基于 N12 日志或 demo 解析监护仪目标参数。
- `JY_monitor_blt_q5` 可基于 Q5 demo 主动连接设备，完成查询/心跳并解析监护仪目标参数。
- `JY_anesthesia_mindray_wato_ex55` 可基于 EX35/EX55 日志或 demo 解析麻醉机目标参数。

### 12.4 参数映射

- 映射配置位于 txt 资源文件。
- 修改原始编码到目标参数编码的映射不需要改 Java 代码。
- 未映射参数不会写入 `device_data`。

### 12.5 数据落库

- 采集结果写入 `${aims.jd.schema}.device_data`，当前配置为 `public.device_data`。
- `param_code` 只出现第 7 节定义的目标编码。
- `dept_id` 和 `device_id` 与对应设备定义一致。
- `recorded_at` 使用服务器 UTC 时间。
- `recorded_str` 保留可展示的字符串值。
- 同一分钟内重复上报按首次结果入库，后续结果跳过。
- `device_data` 仅保留最近 90 天。

## 13. 已决策点

- `aims_jd` 直接读写 AIMS 引擎 schema；`device_infos` 只读，不复制本地快照。
- 当前 schema 配置为 `aims.engine.schema=public`、`aims.jd.schema=public`。
- `aims_jd\src\main\resources\config\db\schema.postgresql.sql` 仅保留可选索引 SQL，不创建业务表。
- EX35/EX55 统一配置为 `JY_anesthesia_mindray_wato_ex55`，不单独新增 `JY_anesthesia_mindray_wato_ex35` 驱动编码。
- `source_mode = 3` 初版完全忽略，不按 `upstream_device_id` 做中央站扇出关联。
- 入站 TCP 使用全局 `tcp.server.port`，不按设备单独监听端口。
- 直接采集设备要求 `device_ip` 唯一，入站连接按 IP 匹配设备定义。
- 宝莱特 Q5 的心跳、查询报文、查询周期、时间戳后缀格式做成 `application.properties` 配置，默认参考 Java demo。
- N12、Q5、EX35/EX55 的原始观测编码初版先基于 demo 和日志给出初始映射；运行时打印解码后的原始消息，便于后续补齐。
- 体温等需要单位统一的参数，入库前统一为摄氏度。
- `recorded_at` 写入 PostgreSQL `TIMESTAMP` 时使用服务器 UTC 时间。
- HL7 中空值、`INV`、`X`、非数值、状态类 OBX 跳过，不写入 `device_data`。
- 同一设备、同一参数、同一分钟内只写入首次结果；同分钟后续更新跳过；分钟数加 1 后再写数据库。
- `device_data` 保留最近 90 天数据。
- `device_data` 90 天清理由外部定时任务或数据库运维手工 SQL 执行，`aims_jd` 初版不内置清理调度。
- 可选索引 SQL 手工执行，不引入 Flyway/Liquibase。
- MLLP/HL7 成功接收时使用 `AA` 作为 ACK，表示接收成功。
